## Part 1 (p12-26) Product & lifecycle
- Marketplace, three sides (captains, customers, platform rules). Growth loop (more captains -> shorter pickup -> more bookings -> more rides/captain).
- Two charging models: commission (15-30%) vs daily subscription (Rs 9-15/24h autos). Both go through an append-only ledger.
- Three apps (Captain Android, Customer Android/iOS, Admin web) never talk directly; three ways messages move: HTTPS request/response, server push (WebSocket/FCM), backend events (Kafka). Why not direct: trust, rules, privacy (masked numbers), records.
- Lifecycle 25 steps in 4 stages: Joining (register, OTP, profile, KYC, licence/vehicle docs, bank penny-drop, activation), Working (online gate checks, GPS every 5s with validation accuracy>50m reject, receive offer within 1/2/3 km expanding, accept via conditional update, navigate w/ geofence 100 m, PIN check, start, live tracking w/ safety rules, reach drop, complete idempotently with server GPS trail), Getting paid (final fare w/ rate-card version pinned at booking, paise; cash/UPI; commission; earnings summary eventual consistency + Redis cache 30s; incentives dedupe by ride id; wallet ledger; payout with Idempotency-Key + reconciliation), Trust & safety (ratings unique per ride/direction, rolling avg last 100; complaints with evidence timeline; suspension with audit log, appeal to a person).
- State machines: onboarding REGISTERED->PROFILE_DONE->DOCS_SUBMITTED->UNDER_REVIEW->APPROVED/NEEDS_FIX->ACTIVE->SUSPENDED/DEACTIVATED; ride REQUESTED->SEARCHING->ASSIGNED->DRIVER_ARRIVING->ARRIVED->IN_PROGRESS->COMPLETED. "A bug cannot jump states not on the list."
- OTP: secure random, hash stored in Redis w/ 5-min TTL, rate limits 3 sends/10 min, 5 wrong tries lock; access JWT 15 min + refresh 30 days.
- Sawari relevance: actors (passenger, assistant, data system, admin, providers, contributors); no marketplace/money; state machines apply to route data lifecycle & conversation; versioned rate card pinned to estimate -> fare_rule_version pinned per itinerary; append-only evidence ~ ledger; audit log; idempotency for feedback/admin.

## Part 6 (p84-94) Matching
- Good match = not just nearest; goals in order (fast pickup, accepted first time, not cancelled, fair spread, city-wide low waits).
- Signals table: Signal / What it means / How measured / Filter or score. Hard filters first (fresh <30 s, availability, vehicle type, docs, wallet, blocks), then scores.
- "Why distance alone fails": railway tracks/flyovers; road ETA carries most weight.
- Illustrative weights (invented, tuned by experiments): ETA 0.55, acceptance 0.15, reliability 0.10, rating 0.10, waited longest 0.05, heading 0.05. Each sub-score normalised 0..1 with explicit formula. Bayesian smoothing: (accepted + 0.8*10)/(offered + 10).
- Worked example table (5 captains; 3 filtered with reason; 2 scored step by step: Ravi 0.745 vs Manoj 0.525). Interview tip: filters first, scores second, in a small table.
- Dispatch strategies: sequential, simultaneous (broadcast), batch (Hungarian assignment); hybrid. Timeouts: offer 15 s + 1 s grace (server-enforced expires_at); search limit 90 s -> EXPIRED.
- Flowchart of the dispatch loop; change-of-mind event table (ride status / captain / money). Re-matching = same loop with memory of who said no; widen radius; report low supply.
- Race conditions: check-then-act bug; fix = one atomic conditional UPDATE in DB (+ offer still live check), transaction rolls back loser; partial unique index one active ride per captain; optimistic locking version column; pessimistic SELECT FOR UPDATE; Redis lock SET NX PX only as a fast filter; fencing; "the database is the final referee".
- Full pseudocode with constants block; loop state in Redis for crash resume; every decision logged with candidates+scores for offline replay.
- Sawari adaptation: route planner = filters (suspended/retired routes, stale, max walk, max transfers) then generalised-cost score with documented weights; worked example table in docs; constants block; deterministic tie-break; log candidates+scores in trip_searches.result; optimistic locking (version) for admin route edits; unique constraints.

## Part 13 (p202-214) Security & privacy
- Three questions: authentication / authorization / protection. Attacker table (attacker / goal / main defence).
